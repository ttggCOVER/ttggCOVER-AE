# DESIGN.md — 学生管理系统

> 这是 Austin Education 招聘技术作业的 Part A。读完它，产品和设计同事应该知道要做什么、为什么、长什么样。

## 1. 我对这个业务的理解

读完三遍背景后，我把"教育机构"这个业务抽象成**一条管道 + 三个角色**：

### 三个角色

| 角色                   | 真实身份      | 他们每天最在意什么                                |
| -------------------- | --------- | ---------------------------------------- |
| **admin**（课程顾问 / 教务） | 销售 + 项目经理 | "我手上 100 个学生，今天哪个该联系？哪个试听完没跟进？哪个快用完课时了？" |
| **teacher**          | 老师本人      | "今天我几节课？每个班谁是谁？新来的学生什么底子？"               |
| **家长 / 学生**          | 客户        | 想要"我家孩子被好好管"的感觉                          |

> **背景没明说但显然存在的东西**：
>
> - **家长和学生不是同一个人**。家长是付费决策者，学生是上课的人。所以学生表必须有 `parent_name` / `parent_phone`。
>
> - **试听和正式课是两件事**。试听是一对一、临时排的、不扣课时；正式课是固定班级、按周重复、扣课时。两类课时间冲突都不能排。
>
> - **课时是钱**。学生买的是 N 节课的"分钟额度"，每节课扣一段。课时余额是机构对客户的负债，不能算错。
>
> - **admin 之间有归属关系**。每个学生有"专属顾问"，怕撞单、怕抢业绩。但 admin 之间能"看到"对方的学生（横向协作）。
>
> - **流失是不可逆状态**。流失的学生不能再排试听 / 进班（除非重新激活）。

### 核心流程（管道）

```
咨询 ── 安排试听 ── 试听完成 ── (老师反馈 + AI 抽取) ── admin 跟进 ── 报名购课
                                                                      │
                                                                      ▼
                                                              排进固定班级
                                                                      │
                                                              每周上课记出勤扣课时
                                                                      │
                                                              余额低 ──> 续费
                                                              或 ──> 流失
```

这条管道上**最容易出问题的三处**：

1. **咨询 → 试听**：忘记安排试听，咨询线索烂在池子里。
2. **试听 → 跟进**：试听完老师反馈没人看，家长等不到回信就跑了。
3. **课时快用完 → 续费**：没人盯余额，课时用完了才发现。

我的切片选的就是**前两处**（咨询 → 试听 → 跟进），它是漏斗的入口，最值钱。

## 2. 我决定要解决的问题和不解决的问题

### 第一版要做（本作业切片覆盖到）

- **学生完整生命周期**：咨询登记 → 安排试听 → 试听反馈 → AI 抽取结构化结果 → 自动派发 admin 跟进任务 → 确认报名 → 班级出勤扣课时 → 续费预警

- **核心规则服务端强制**：试听只能一次、时间冲突、流失学生不能排试听、admin 权限隔离、课时不透支

- **admin 工作台**：漏斗卡片（可点击进入列表）、课时预警、过期跟进高亮

- **老师工作台**：今日课程、今日试听、待反馈/已反馈试听；班级考勤页（名单 + 出勤 + 扣课时）

- **一处 LLM**：试听反馈结构化抽取（紧贴业务流，不是为用而用）

- **数据真实性**：所有工作台数字均来自 DB 真实查询（按 owner 过滤），无硬编码

### 第一版**故意不做**（重要但可后做）

| 不做                        | 为什么                                                                                          |
| ------------------------- | -------------------------------------------------------------------------------------------- |
| **续费 / 流失的主动决策 UI**       | 规则落地了（不能给 churned 排试听 = R6），报名时自动建 30 天后续费跟进任务，但"主动标记续费/流失"的决策 UI 留到下一版。                     |
| **班级管理 / 排进班级的 admin UI** | 班级表 + class\_members 多对多建好，seed 已把 enrolled 学生排进班，但没有 admin 手动排班/调班 UI。报名后自动进班由 seed/报名接口处理。 |
| **多 admin 协作 / 转单**       | 第一版 `owner_admin_id` 固定，转单需要历史记录和审批流。                                                        |
| **老师请假 / 调课**             | 这是运营层流程，不进系统核心。                                                                              |
| **微信集成 / 短信通知**           | 出切片范围，是外挂渠道。                                                                                 |
| **多时区切换**                 | 作业明确说不需要，统一 Melbourne。                                                                       |
| **报表 / BI**               | 等数据攒起来再说。                                                                                    |

> **砍掉的原则**：凡是"规则"已经在代码层落地的，UI 不做不影响"业务能跑通"；但**只在前端禁用按钮、后端不拦**的，绝不算数。

## 3. 数据模型

### ER 总览

```
users ──< students ──< consultations
                 │
                 ├──< trial_bookings >── users (teacher)
                 │           │
                 │           └── (LLM 抽取结果写入 extracted_feedback JSON)
                 │
                 ├──< class_members >── classes ── teacher (users)
                 │                          │
                 │                          └──< class_sessions ──< attendance >── students
                 │
                 ├──< lesson_credits (1:1 余额)
                 │           │
                 │           └──< lesson_transactions (流水账)
                 │
                 └──< follow_ups ── owner (users:admin)
```

### 关键表 + 关键字段

| 表                     | 关键字段                                                                                                                                   | 说明                                                                        |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `users`               | id, role('admin'\|'teacher'), email, password\_hash, dept                                                                              | admin 和 teacher 共用一张表，role 区分                                             |
| `students`            | **parent\_name**, parent\_phone, grade, **status**, **owner\_admin\_id**, notes                                                        | ★ 家长和学生分开；★ owner 决定权限                                                    |
| `consultations`       | student\_id, channel, source, need, created\_by                                                                                        | 一个学生可以多次咨询（咨询可能反复来）                                                       |
| `trial_bookings`      | student\_id, teacher\_id, scheduled\_at(ISO UTC), duration\_min, status, feedback\_text, **extracted\_feedback(JSON)**, recommendation | ★ partial unique index on (student\_id) WHERE status='completed' 保证试听只能一次 |
| `classes`             | teacher\_id, weekday(0-6), start\_time, end\_time, subject, capacity                                                                   | 每周固定模板                                                                    |
| `class_members`       | (student\_id, class\_id) PK                                                                                                            | 多对多                                                                       |
| `class_sessions`      | class\_id, session\_date(YYYY-MM-DD), status('scheduled'\|'completed'\|'cancelled')                                                    | 每次实际开课一条；同班同日唯一                                                           |
| `attendance`          | session\_id, student\_id, status('present'\|'absent'\|'late'), minutes\_deducted, note                                                 | 每学生每节课一条；出席/迟到扣课时，缺席不扣                                                    |
| `lesson_credits`      | student\_id PK, balance(int 分钟), **CHECK (balance >= 0)**                                                                              | ★ 余额冗余存储，DB 约束兜底防透支                                                       |
| `lesson_transactions` | student\_id, delta\_min, reason, ref\_class\_session\_id                                                                               | 流水账，不可篡改                                                                  |
| `follow_ups`          | student\_id, type, content, due\_at, done\_at, owner\_admin\_id, trial\_booking\_id                                                    | 跟进任务                                                                      |

### ★ 三个关键问题的回答

**Q1：一个学生同时在两个班？**
答：允许。`class_members` 是多对多。但要保证**不冲突**——同一学生在 weekday + 时间段重叠的两个班不允许（R2 业务层校验）。

**Q2：课时怎么退？**
答：`lesson_transactions` 加一条 `reason='refund'` 的正数记录，同时 `UPDATE lesson_credits SET balance = balance + delta`。退到负数会被 CHECK 拦。流水账保留审计痕迹。

**Q3：试听只能一次怎么实现？**
答：DB 层 partial unique index：

```sql
CREATE UNIQUE INDEX uniq_trial_completed_per_student
  ON trial_bookings(student_id) WHERE status = 'completed';
```

业务层先 check（`assertOnlyOneCompletedTrial`），DB 兜底。即使业务层有 bug，DB 也拦得住。

## 4. 关键规则（≥5 条，全部服务端强制）

| #      | 规则                                                                               | 执行层                                | 实现位置                                                                 |
| ------ | -------------------------------------------------------------------------------- | ---------------------------------- | -------------------------------------------------------------------- |
| **R1** | 同一学生只能有 1 条 `status='completed'` 的试听                                             | DB partial unique index + 业务层事务    | `server/src/lib/rules.ts#assertOnlyOneCompletedTrial` + `schema.sql` |
| **R2** | 排课时间冲突：同一学生在同一时间段的 trial\_booking 或 class\_member 不能重叠                           | 业务层（事务内查询 + 时间区间比较）                | `server/src/lib/rules.ts#assertNoScheduleConflict`                   |
| **R3** | admin 只能修改 `owner_admin_id = req.user.id` 的学生；可查询全部学生（列表用 owner\_admin\_id 标记归属） | 路由层 + 业务层（写操作前后双校验）                | `students.ts#PATCH` 调用 `assertAdminOwnsStudent`                      |
| **R4** | 课时余额不能透支（balance >= 0）                                                           | DB CHECK 约束 + 业务层事务（先查再扣，CHECK 兜底） | `schema.sql CHECK (balance >= 0)` + `rules.ts#consumeLesson`         |
| **R5** | 试听反馈只能由 `trial_bookings.teacher_id = req.user.id` 的老师提交                          | 路由层所有权校验                           | `rules.ts#assertTeacherOwnsTrial`                                    |
| **R6** | 不能给 `status='churned'` 的学生排试听/进班                                                 | 业务层校验                              | `rules.ts#assertStudentNotChurned`                                   |
| **R7** | follow\_ups.due\_at 必须晚于当前时间                                                     | 业务层校验                              | `rules.ts#assertFollowUpDueAfterNow`                                 |

**为什么这么分层**：

- **DB 约束**用于"任何业务代码都改不动"的硬规则（R1 / R4），防业务层 bug + 防直接 SQL 改库。

- **业务层**用于"需要查询上下文才能判定"的规则（R2 / R3 / R5 / R6 / R7）。

- **绝不**只在前端禁按钮——作业明确说"我们会绕过界面直接测"。

## 5. 我的假设和问题

### 我做的假设

1. **试听"只能一次"指** **`completed`** **状态只能一次**。`pending`（已排未上）的可以有多条（虽然业务上很少见）。如果业务方说"pending 也只能一条"，改 partial unique 去掉 WHERE 子句。
2. **每个学生只有一个归属 admin**。背景说"每人手上 100 学生"，没明说能不能共享，我按"单一归属"做。如果要做转单，需要 `student_owner_history` 表。
3. **试听不扣课时**。试听是销售活动，不消耗已购买课时。
4. **班级是每周固定模板**（weekday + 时间），不是某一周的临时课。具体某周的课是 `class_sessions`（本作业未实现）。
5. **老师不能修改试听时间**，只能取消 / 标记完成 / 提交反馈。改时间要 admin 来（怕老师乱改）。
6. **AI 抽取失败不应阻塞主流程**。所以降级返回 `recommendation='pending'`，admin 自己看反馈判断。
7. **课时单位是分钟**，不是节课。不同课时长不同，用分钟最灵活。
8. **流失学生重新激活**走 admin 手动 PATCH `status`，不进本切片。

# 我最想问业务方的 3 个问题



1. **admin 之间能不能互相改学生？** 
2. **AI 抽取的** **`recommendation`** **谁有权改？** 
3. **流失定义是"主动不续费"还是"超过 N 天没联系"？**

## 7. Part B 的选择理由

我选**咨询 → 安排试听 → 试听反馈 → AI 抽取 → 跟进 → 报名 → 班级出勤扣课时** 这条完整流程，因为：

1. **它是漏斗的入口也是核心变现路径**。教育机构的 LTV 从咨询开始，到报名购课、持续上课扣课时才完成变现。入口和变现都做好，业务才闭环。

2. **它有最自然的 LLM 落地点**。老师写的试听反馈是自由文本，admin 没空细读，AI 抽取结构化结果 + 自动派跟进任务，是**真正省人力**的位置——不是"为了用 AI 加了个聊天框"。

3. **它覆盖了所有 7 条业务规则**：

   - R1 试听只能一次

   - R2 排课冲突

   - R3 admin 权限隔离

   - R4 课时不透支（报名建余额、出勤扣课时、余额不足拦截）

   - R5 老师所有权

   - R6 流失学生不可排试听

   - R7 跟进到期时间校验

4. **它能演示破坏测试**。绕过前端直接 POST `/api/trials` 给同一学生排第二次 completed → 拦；用 admin A 的 token 改 admin B 的学生 → 拦；给 churned 学生排试听 → 拦；余额不足仍提交考勤 → R4 拦；同班同日重复考勤 → SESSION_DONE 拦。

5. **它"窄而透"**。从 DB → 服务端规则 → 路由 → 前端 UI → LLM 调用 → 降级链路完整打通，每一步都能解释。

**LLM 落地点的选择理由**：试听反馈抽取而非课堂反馈润色。试听反馈是**决策依据**（决定报不报名），需要结构化；出勤是过程产物，不需要 AI。所以 AI 放在试听反馈页，扣课时走纯规则（R4）。

## 8. AI 工具的使用说明

详见 README.md「AI 工具使用」一节。简而言之：

- 全程使用 **TRAE（GLM 模型）** 开发，包括方案设计、代码生成、调试。

- **采纳**：数据模型设计、规则分层（DB vs 业务层）、降级链路（zod + HTTP 200 + `_degraded:true`）。

- **没采纳**：AI 建议用 Prisma ORM，我没用——SQLite + `node:sqlite` 直接写 SQL 更简单、对单文件部署更友好；AI 建议用 better-sqlite3，我改用 Node 22 内置 `node:sqlite`（避免 Windows 原生编译问题）；AI 建议"AI 抽取失败返回 500 让前端报错"，我改成降级返回 200 + `_degraded`，因为业务要求"AI 失败不能阻塞主流程"。
